01

Scope & Non-Goals

We build

  • A desktop-style dashboard: corridor selector, date range, k_factor slider, green Execute National Fare Audit button, live terminal console.
  • A 5-stage backend pipeline: AI-augmented web scraping → festival flagging → IQR purification → weighted Laspeyres → resilient persistence.
  • A reproducible airfare price index (base = 100), with a festival-adjusted variant and a history chart.
the problem statement mandates scraping

SIH26056, verbatim: "Development of a Real-time Airfare Price Index for India through Automated Web Scraping of Airline and Online Travel Aggregator Portals." MoSPI is explicitly asking for a scraper of MakeMyTrip / Ixigo / Cleartrip / IndiGo / Air India. An earlier draft of this doc pitched "we never scrape, we use APIs" — that was solving a problem the judges did not set. Web scraping is the primary acquisition method. §2A is how we do it well.

We deliberately do NOT build

  • No price forecasting. This is measurement of history, not prediction. The nowcasting model (§2A) imputes missing observations — it never forecasts future prices.
  • No reckless scraping. robots.txt honoured, rate-limited (1 req / few seconds per domain), realistic UA, off-peak, results cached hard. Scraping for a public-statistics purpose the PS itself specifies — not for resale.
  • No multi-user / auth / cloud deploy. Single-operator local app is the whole brief.
  • No microservices. One FastAPI process. One port.

2A

AI-Augmented Web Scraping

The PS mandates web scraping (§01). Our mentor wants an AI angle. Both are satisfied by the same thing: a Playwright scraper whose extraction layer is a vision-language model — it IS web scraping, and it self-heals when a site changes its HTML, which a selector-based scraper cannot. This section supersedes the acquisition choices above where they conflict.

the synthesis

PS: "through Automated Web Scraping of Airline and OTA Portals." Mentor: "make it advanced, make it AI." Answer: AI-augmented scraping — Playwright drives a real browser (scraping ✓), and an LLM/vision model reads the rendered page to extract fares regardless of layout (AI ✓, and genuinely more robust than CSS selectors).

what to say in the interview

"We scrape airline and OTA portals as the problem statement specifies — MakeMyTrip, Ixigo, Cleartrip, IndiGo, Air India — using headless browsers that intercept each site's own fare API. What makes it robust is the extraction layer: instead of brittle CSS selectors we use a vision-language model that re-derives the fields when a site changes its layout, so the scraper self-heals. On top sit three models: an anomaly detector for decoy/placeholder fares, a nowcasting model that fills scraping gaps with confidence bands, and an LLM that attributes every index movement to a cause. We scrape responsibly — robots.txt, rate limits, off-peak, aggressive caching."

what will fail — do not do this

Don't scrape all five sources live during the demo. Slow (~5–15 s/search each), flaky, and one captcha kills it on stage. Pre-scrape four into the cache the night before; live-scrape ONE — pick the lightest anti-bot (Ixigo, or an airline site directly). Rehearse the fallback: if the live scrape is blocked, it drops to cache — demo that as a feature.

Don't reverse-engineer XHR params and replay with bare httpx as the primary path. Sites rotate tokens/cookies and it breaks silently. Drive a real browser; intercept the response.

Don't call the nowcasting model "prediction." It is imputation. "We forecast prices" loses the "we measure, not predict" high ground instantly.

Impact on the module specs (§07)

  • 7.1 Ingestion → Scraper pool. fetch_fares() fans out to per-source Playwright adapters (concurrent), merges + dedupes, returns the same list[dict] contract. Each adapter: browser → intercept XHR → (on schema break) vision-LLM extract → normalise. Per-source failure → newest cached scrape for that route.
  • 7.3 IQR Purifier → "IQR + Isolation Forest." IQR stays as the transparent, hand-checkable baseline; the ML model runs on top and can flag decoy/placeholder fares IQR misses. Both logged, nothing silently deleted.
  • New 7.8 — Nowcasting & Explainability. After Laspeyres. Imputes missing route-days (confidence bands), then an LLM writes a one-line cause. Optional / "if time permits" — the index is valid without them.

Festival flagging, weighted Laspeyres, Postgres/SQLite failover, and the SSE console are unchanged.

Why pipeline/ is separate from app/

Request Lifecycle

Exactly what happens between clicking Execute and seeing the index.

  1. Click. app.js builds a query string and opens new EventSource("/api/execute-audit?..."). Button disables, console clears.
  2. Validate. FastAPI parses query params into the AuditParams Pydantic model. Bad input → 422 before any pipeline code runs.
  3. Stream opens. Route returns StreamingResponse(run_audit(params), media_type="text/event-stream").
  4. Orchestrator runs. The async generator run_audit executes each stage and yields one SSE line after it, with a 0.2s pause so the console visibly streams: 
    [SYSTEM]    Audit started · DEL-BOM · run a1b2c3d4
[SCRAPE]    pool · 5 sources · 412 fares merged
[FESTIVAL]  38 fares flagged (Diwali: 31, Christmas: 7)
[IQR]       k=1.5 · fences [3200, 7600] · 2 anomalies excluded
[LASPEYRES] Index = 118.75 · ex-festival = 116.40
[DB]        Postgres commit OK
[SYSTEM]    Audit complete — Index = 118.75
  5. Frontend reacts. Each es.onmessage appends a line. The final message carries done:true, index, index_ex_festival → show the big number, refresh the chart, close the stream, re-enable the button.

Each: the job in plain words, the code shape, a worked example where numbers matter, the log line, and the interview questions it invites.

7.1  Scraper Pool — pipeline/scrape/

Job: given a corridor and a date range, scrape airline + OTA portals and return a list of fare records. Fan out to one adapter per source, merge, dedupe. Per-source failure → newest cached scrape. (§2A has the full architecture.)

record shape — the contract every later module depends on
{
  "flight_id":    "6E-2341-20261108",
  "route":        "DEL-BOM",
  "price":        5480.0,
  "currency":     "INR",
  "departure_ts": "2026-11-08T06:15:00+05:30",
  "airline":      "6E",
  "source":       "ixigo"          # or makemytrip / cleartrip / indigo / airindia / cache
}
logic
fetch_fares(corridor, date_range) -> (records: list[dict], sources: dict)

  adapters = [MakeMyTrip, Ixigo, Cleartrip, IndiGo, AirIndia]
  results  = await gather(*[a.scrape(corridor, date_range) for a in adapters])
  records, sources = merge_dedupe(results)          # key: airline+flight_no+departure_ts
  return records, sources

# --- one adapter ---------------------------------------------------
class SourceAdapter:
  async def scrape(corridor, date_range) -> list[dict]:
    key = f"{self.name}_{corridor}_{date_range}"
    for date in date_range:
      try:
        page = await browser.new_page()
        captured = []
        page.on("response", lambda r: captured.append(r) if self.is_fare_xhr(r) else None)
        await page.goto(self.search_url(corridor, date))
        await page.wait_for_selector(self.results_ready)     # fares rendered

        try:                                                  # FAST path
          data = await captured[-1].json()
          records += self.parse_xhr(data)
        except (IndexError, KeyError, JSONDecodeError):        # SELF-HEALING path
          shot = await page.screenshot(); dom = await page.inner_text("body")
          records += await llm_extract(shot, dom, schema=FARE_SCHEMA)

      except (TimeoutError, PlaywrightError, Blocked):         # FALLBACK
        return load_cache(key) or []
    write_cache(key, records)
    return records
why intercept the XHR instead of parsing HTML

MakeMyTrip/Ixigo/etc. are single-page apps — the fare list is drawn by JavaScript from the site's own JSON API. We let a real Chromium load the page (which passes most bot checks and executes that JS), then read the JSON response directly. Clean structured data, no CSS-selector soup. The vision-LLM path only fires when that JSON shape changes.

responsible scraping — build it in, say it out loud

One request every few seconds per domain · realistic rotating User-Agent · read and honour robots.txt and Retry-After · schedule bulk scrapes off-peak · cache every response so the demo and re-runs don't re-hit the sites. This is scraping for a public-statistics purpose the problem statement itself specifies — not for resale or competitive harm.

Q — "Scraping OTA sites — isn't that against their terms?"

The problem statement explicitly directs us to scrape airline and OTA portals for a national CPI input — a public-interest, government-statistics use. We scrape responsibly: robots.txt, rate limits, off-peak, no resale. In production MoSPI would formalise this with data-sharing MoUs; the prototype demonstrates the acquisition method the PS specifies.

Q — "What happens when a site changes its layout?"

A selector-based scraper would silently break. Ours has two extraction paths: normally we read the site's own JSON response; when that shape changes, a vision-language model reads the rendered page and re-derives the fields. The scraper self-heals — no overnight selector maintenance.

Q — "How is this real-time if the demo runs on cache?"

The scrapers run on a schedule and write the cache continuously; the index reads the freshest available. On stage we scrape one source live to prove the path, and serve the rest from cache that's minutes-to-hours old — well inside tolerance for a monthly CPI input.

7.2  Festival Flag Engine — pipeline/festival.py

Job: mark each fare that departs within ±7 days of a major Indian festival, so an analyst can compute the index with and without festival demand.

build_festival_dates(year) -> list[(name, date)]
  import holidays
  ind = holidays.India(years=[year, year+1])
  keep = {"Diwali", "Holi", "Dussehra", "Christmas Day",
          "Guru Nanak Jayanti", "Eid al-Fitr", "Eid al-Adha"}
  return [(name, d) for d, name in ind.items() if name in keep]

flag_festivals(records, festival_dates, window_days=7) -> (records, flagged_count)
  for r in records:
      dep = date(r["departure_ts"])
      r["is_festival_season"] = 0 ; r["festival_matched"] = None
      for name, fdate in festival_dates:
          if abs((dep - fdate).days) <= window_days:
              r["is_festival_season"] = 1 ; r["festival_matched"] = name ; break
  flagged_count = sum(r["is_festival_season"] for r in records)
  return records, flagged_count
log line
[FESTIVAL] window=±7d · 38 fares flagged (Diwali: 31, Christmas: 7)
verify before demo

Write a test that asserts the 2026 dates holidays returns against a real calendar. Note in the deck that Eid is lunar and the library must be kept current.

Q — "Why ±7 days, not the exact date?"

Airfare demand ramps before and stays elevated after a festival — people travel home in the days around it. ±7 days captures the demand window; it's a config parameter, not a magic constant.

Q — "Why is this analytically useful, not cosmetic?"

It lets you decompose the index: index_all vs index_ex_festival. The gap is the transient holiday-demand component — exactly what a statistical office wants separated from structural price change.

7.3  Dynamic IQR Purifier — pipeline/iqr.py

Job: remove data-error prices (glitch-low and absurd-high) before they poison the average, using a standard statistical rule with a tunable knob.

apply_iqr_filter(records, k_factor) -> (clean, anomalies, fences)
  prices = [r["price"] for r in records]
  Q1 = numpy.percentile(prices, 25)
  Q3 = numpy.percentile(prices, 75)
  IQR = Q3 - Q1
  lower_fence = Q1 - k_factor * IQR
  upper_fence = Q3 + k_factor * IQR

  for r in records:
      if lower_fence <= r["price"] <= upper_fence:  clean.append(r)
      else:
          r["exclusion_reason"] = "below_lower_fence" if r["price"] < lower_fence else "above_upper_fence"
          anomalies.append(r)
  return clean, anomalies, {Q1, Q3, IQR, lower_fence, upper_fence}

Q — "Why IQR and not standard deviation / z-score?"

Airfares are right-skewed (a long tail of expensive last-minute/business fares). Mean and std-dev are dragged by that tail, so a z-score rule throws away legitimate high fares. Quartiles are robust to skew — that's why Tukey's IQR rule is standard for skewed data.

Q — "What if an analyst sets k_factor wrong?"

It's exposed precisely so they can audit it. Anomalies are logged and stored, never deleted — the count and the rows are kept, so any k choice is reversible and reviewable.

Q — "Why a lower fence?"

Fare-error data (₹1, nulls read as 0, placeholder responses) shows up as impossibly low prices. Screening only the top tail would let those through and bias the index downward.

7.4  Weighted Laspeyres Engine — pipeline/laspeyres.py

Job: combine per-route average current prices into one national index, weighting each route by how much traffic it actually carries.

Index = [ Σ(Pt · Q0) / Σ(P0 · Q0) ] × 100

Pt = current avg price on a route (after IQR cleaning)
P0 = base-year avg price on that route      (base_year_reference.json)
Q0 = base-year passenger volume on that route (fixed weight, from DGCA)
compute_index(clean_records, base_ref) -> (index, table)
  df = DataFrame(clean_records)
  pt = df.groupby("route")["price"].mean().rename("Pt")
  base = DataFrame(base_ref).T                     # index=route, cols P0, Q0
  merged = base.join(pt, how="inner")              # only routes in both
  merged["pt_q0"] = merged.Pt * merged.Q0
  merged["p0_q0"] = merged.P0 * merged.Q0
  index = 100 * merged.pt_q0.sum() / merged.p0_q0.sum()
  return round(index, 2), merged
worked example — put in test_laspeyres.py 
            Pt      P0      Q0
DEL-BOM    5750    5000    1000
DEL-GAU    9000    6000     100     # small route, big % jump

numerator   = 5750·1000 + 9000·100 = 6,650,000
denominator = 5000·1000 + 6000·100 = 5,600,000
Laspeyres index = 6,650,000 / 5,600,000 × 100 = 118.75

Naive average of price ratios = (5750/5000 + 9000/6000)/2 = 1.325 → 132.5

The naive number is 14 points higher because it lets a tiny route swing the national figure. Laspeyres correctly says the route 1000 people fly matters 10× more than the route 100 people fly.

log line
[LASPEYRES] 5 routes matched · Index = 118.75 (base 2022 = 100)
Q — "Why Laspeyres, not Paasche or a chained index?"

Laspeyres fixes the weights at the base year (Q0), so period-to-period moves reflect price change only, not shifting travel patterns. That's how CPI itself is built, which makes our number directly comparable to CPI.

Q — "Why groupby/merge instead of a loop?"

Vectorised pandas is reproducible and auditable — same input always gives the same output, and the intermediate Pt/P0/Q0 table is inspectable. A nested loop is harder to verify.

Q — "Where do P0 and Q0 come from?"

P0: average 2022 fares per route from a public historical dataset (our base period). Q0: DGCA's published airport-pair domestic passenger volumes. Both external, cited, frozen in base_year_reference.json.

7.5  Persistence — pipeline/persistence.py

Job: save the run. Try Postgres; if it's down, transparently write SQLite so a DB outage never freezes the app.

persist_run(run_data) -> str
  try:
      engine = create_engine(PG_DSN, connect_args={"connect_timeout": 3})
      with engine.begin() as conn:
          conn.execute(insert(audit_runs), run_data)
      return "postgres"
  except (OperationalError, DBAPIError, TimeoutError) as e:
      conn = sqlite3.connect("db/fallback.sqlite")
      conn.execute("PRAGMA journal_mode=WAL")
      conn.execute("INSERT INTO audit_runs ...")
      conn.commit()
      return "sqlite_fallback"
log lines
[DB] Postgres commit OK · run_id=a1b2c3d4
[DB][FALLBACK] Postgres unreachable (connection refused) → SQLite WAL commit OK
what is WAL?

Write-Ahead Logging — SQLite writes changes to a side -wal file first, then folds them into the main DB. A reader and a writer don't block each other, and a crash mid-write can't corrupt the database. For the demo: the row is durable the instant we commit.

Q — "What if BOTH databases fail?"

(Answer honestly.) SQLite is a local file, so a true dual failure means the disk is gone. We'd need an in-memory retry queue that flushes when a DB returns — that's stated future work, not something we claim is solved.

Q — "Isn't SQLite a downgrade?"

It's a resilience net, not a replacement. Postgres stays authoritative; the row is tagged db_target='sqlite_fallback' so you always know which store holds it and can reconcile later.

7.6  Orchestrator — app/orchestrator.py

The heart. An async generator that runs the whole pipeline and yields one SSE line per stage. The only file that knows about streaming.

def sse(stage, message, **extra):
    return f"data: {json.dumps({'stage': stage, 'message': message, **extra})}\n\n"

async def run_audit(params):
    run_id = str(uuid.uuid4())
    yield sse("SYSTEM", f"Audit started · {params.corridor} · run {run_id[:8]}", run_id=run_id)
    await asyncio.sleep(0.2)

    records, source = await fetch_fares(params.corridor, params.date_range)
    yield sse("INGEST", f"{source} · {len(records)} fare records");            await asyncio.sleep(0.2)

    records, fcount = flag_festivals(records, FESTIVALS)
    yield sse("FESTIVAL", f"{fcount} fares flagged (±7d)");                     await asyncio.sleep(0.2)

    clean, anomalies, f = apply_iqr_filter(records, params.k_factor)
    yield sse("IQR", f"k={params.k_factor} · fences [{f['lower']:.0f},{f['upper']:.0f}] · {len(anomalies)} excluded")
    await asyncio.sleep(0.2)

    index, table  = compute_index(clean, BASE_REF)
    index_exf, _  = compute_index([r for r in clean if not r["is_festival_season"]], BASE_REF)
    yield sse("LASPEYRES", f"Index = {index} · ex-festival = {index_exf}");     await asyncio.sleep(0.2)

    target = persist_run({...})
    yield sse("DB", f"commit OK → {target}")
    yield sse("SYSTEM", f"Audit complete — Index = {index}", done=True, index=index, index_ex_festival=index_exf)
why this design

Pipeline functions never import FastAPI or a logger. The only place that knows about streaming is this one file. A beginner reads it top to bottom and understands the entire system in 30 lines. The sleep(0.2) calls make the console visibly stream instead of dumping everything at once.
